# 設計書：表示期間「直近24ヶ月」＋セクション並び替え（2026-09-05）

## 背景・目的

ダッシュボードのブラッシュアップ第1弾。ユーザー要望は2点：

1. 表示期間の選択肢に「直近24ヶ月」を追加（2シーズン比較の視点で見たい）
2. 表示セクションの並び替え機能（よく見るカードを上に置きたい）

前提の運用形態：利用者は admin 1名のみ・スマホとPCの両方から閲覧。

## スコープ

**やる**
- 期間セレクタに「直近24ヶ月」（`last24`）を追加
- `last24` のときのKPI比較・トレンド前年重ねの整合を取る
- セクション10ブロックの並び替え（並び替えモード＋↑↓ボタン）と、DASH KV へのサーバー側保存（全端末共通）

**やらない（YAGNI）**
- ドラッグ&ドロップ
- カード単位（GA4/IG内部の個別カード）の並び替え
- セクションの表示/非表示切替（今回は順番のみ）
- 複数ユーザー別の並び順（ユーザーはadmin 1名）

## 機能1：直近24ヶ月

### 期間の定義
- `Period.kind` に `'last24'` を追加。`resolvePeriod('last24', today)` は
  `start = today の24ヶ月前 + 1日`、`end = today`、`label = '直近24ヶ月'`（`last12` と同じ方式で期間だけ24ヶ月）。
- セレクタの表示順：直近12ヶ月 → **直近24ヶ月** → 全期間 → 年別。

### 前年比の整合（重要）
現状の `priorYear()` は一律 -12ヶ月シフトのため、24ヶ月窓では比較期間が表示期間と12ヶ月重複し、比較として成立しない。

- **KPI**: 比較期間を「窓の長さぶん前」にする。新関数 `priorPeriod(p)` を導入し、
  `last24` → -24ヶ月シフト、それ以外（`last12`/`year`/`all`）→ 従来どおり `priorYear` と同じ -12ヶ月。
  `computeKpi` は `priorPeriod` を使う。
- **KPIの比較ラベル**: `last24` のときのみ「前年比」→「**前24ヶ月比**」に変える（他はラベル不変）。
- **トレンドの前年重ね**: `last24` では**非表示**（`priorYearSeries` は `kind === 'last24'` のとき全 `null` を返す）。
  理由：24ヶ月チャートは前年ぶんを自身に含むため、重ねると同じデータの二重描画になり誤読を招く。
  `all`/週次の従来挙動（すでに条件つき）は変更しない。

### GA4/IG への影響
- GA4: `DAILY_SESSIONS_SPEC` の limit は 100000 で24ヶ月（約730行）に対応済み＝**変更不要**（2026-09-05 コード確認済み）。他レポートは期間非依存の集計＝変更不要。
- IG: reach は既存仕様で「期間末尾の≤30日窓にクランプ」＝変更不要。

## 機能2：セクション並び替え

### 並び替え単位（10ブロック・既定順）
| id | セクション |
|---|---|
| `kpi` | KPI サマリー |
| `insights` | 戦略インサイト |
| `trend` | 売上・予約トレンド |
| `heatmap` | 季節×曜日ヒートマップ |
| `weather` | 天候相関 |
| `cohort` | リピーター・コホート |
| `course` | コース別内訳 |
| `source` | 流入経路（自己申告） |
| `ga4` | Web流入（GA4）一式 |
| `ig` | Instagram（SNS）一式 |

期間セレクタのカードは対象外（常に最上部）。GA4/IG は一式を1ブロックとして動かす。

### UI・操作フロー
1. ヘッダーに「並び替え」ボタン（テキストリンク調・ログアウトの左）。
2. 押すと並び替えモード：各ブロックの上部に **↑／↓ボタン**（タップ目標44px以上・スマホ配慮）と「完了」「キャンセル」バーを表示。
3. ↑↓はJSでDOMノードを即時入れ替え（通信なし）。先頭の↑と末尾の↓は無効表示。
4. 「完了」→ `POST /api/section-order` で保存 → 成功したらモード終了＋「並び順を保存しました」を短時間表示。
5. 「キャンセル」→ 保存せずリロード（元の並びに戻る）。
6. 保存失敗（非200/通信エラー）→ `alert('保存に失敗しました。通信環境を確認して再度お試しください')`、モードは維持。

### データ・API
- 保存先: **DASH KV**（`DATA` はread-only維持）。キー `ui:sectionOrder`、値はJSON文字列配列（例 `["trend","kpi",…]`）。
- `POST /api/section-order`（要ログイン・既存セッション認証の内側）
  - body: `{"order": string[]}`
  - 検証: **既知ID集合の完全な並べ替え（全10ID・重複なし・過不足なし）であること**。違反は400（保存しない）。
    ※クライアントは常に画面上の全ブロックの並びを送るため、部分リストは正常系に存在しない。
  - 成功: KVへ全置換保存し `{"ok":true}`。
- GETエンドポイントは作らない（SSRが読むため不要）。

### 並び順の適用（SSR）
- `handleHome` が KV から保存順を読み、`pages.ts` は各セクションを `{id, html}` の配列として構築 → 適用順に並べて `<section data-sec="<id>">` で包んで出力。
- **マージ規則 `applyOrder(defaultIds, saved)`**（将来のバージョンアップでセクションが増減した際に、古い保存データでも壊れないための規則）:
  1. `saved` から既知IDのみ・重複除去で取り出し、これを基礎順とする（削除済みセクションのIDは無視）。
  2. `saved` に無い既定ID（＝保存後に追加された新セクション）は、既定順で処理し、「既定順における直前のID」が基礎順に存在すればその直後に、無ければ先頭に挿入。
  3. KV未設定・JSONパース失敗・空配列は既定順をそのまま使う。
- 例: 既定 `[A,B,C,D,E]`（Eは新設）・saved `[C,A,D,B]`（旧バージョンで保存した完全順） → Eの既定直前はD → Dの直後に挿入 → `[C,A,D,E,B]`。

### 実装配置（1ユニット1責務）
- `src/sections.ts`（新規）: セクションID定義・`applyOrder`（純関数・単体テスト対象）
- `src/handlers.ts`: `handleSectionOrder`（POST検証・KV保存）、`handleHome` に保存順の読込を追加
- `src/index.ts`: 認証内ルートに `POST /api/section-order` を追加
- `src/pages.ts`: セクション配列化・`data-sec` ラップ・並び替えモードのUI＋インラインJS

## エラーハンドリング
- KV読込失敗（DASH障害）→ 既定順で描画（ダッシュボード自体は落とさない。既存の天候/GA4/IGと同じフォールバック思想）
- POSTの不正body → 400・保存なし
- 未ログインのPOST → 既存認証ミドルウェアにより拒否

## テスト計画（TDD）
- `period`: `resolvePeriod('last24')` の窓計算／`priorPeriod` が last24 で -24・他で -12
- `kpi`: last24 のとき前24ヶ月と比較していること
- `trend`: last24 で前年重ねが全null
- `sections.applyOrder`: 保存なし／完全一致／部分保存＋新セクション挿入位置／未知ID無視／重複除去
- `handlers`: POST 正常系（KV保存）・400系（非配列/未知ID/重複）
- `pages`（レンダリング）: 保存順どおりに `data-sec` が並ぶ／last24でKPIラベルが「前24ヶ月比」
- 既存テストの回帰（typecheck + vitest 全件 green）

## デプロイ
実装・レビュー完了後、ユーザー承認を得て `npx wrangler deploy`。デプロイ後にスマホ・PC双方で並び替え→相互反映を目視確認してもらう。
